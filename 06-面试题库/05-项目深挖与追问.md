# 项目深挖与追问

> 本章导读：大模型面试的真实结构，往往是“10 分钟八股 + 40 分钟项目拷打”。面试官不关心你用了什么框架，而是沿着“业务目标 → 数据 → 方案 → 训练/推理 → 评测 → 上线”一路追问，直到确认这件事真的是你做的。本章把公开面经里出现过的项目追问，按项目类型拆成可直接练习的题库。
>
> 使用方式：先选一个你简历上的项目，找到对应类型，逐题自问自答；答不上来的，回到对应专题文档补课。每个项目至少准备一个“失败案例”和一个“量化口径”。

## 核心要点

- 项目答辩的黄金结构：**为什么做 → 怎么做 → 难点与取舍 → 结果怎么量化 → 如果重做怎么改**。
- 面试官最爱追问三件事：**数字怎么算的、基线是什么、失败 case 怎么定位**。只报结论不报口径，会被一路追到底。
- 不要按“技术栈”讲项目，要按“决策链”讲：每个选择都要有替代方案和取舍依据。
- 项目里的每个模块都要能回答“去掉它会怎样”（消融）和“换一种做法会怎样”（对比）。
- RAG/Agent 项目的高频追问集中在：切分与召回、rerank 截断、上下文工程、记忆、工具安全、评测集构造。
- 训练/微调项目的高频追问集中在：显存估算、数据配比、LoRA 超参、不收敛排查、灾难性遗忘、RL 的 reward 设计。
- 推理项目的追问集中在：TTFT/TPOT、KV Cache、吞吐与并发、量化损失、容量规划、故障降级。
- 没有真实项目时，不要编造公司级数据；可以讲复现实验/个人项目，但必须说清“我实际做了什么、环境是什么、数字的边界在哪”。

## 1. 面试官如何挖项目：四层追问法

| 层级 | 追问 | 考察点 | 常见失分 |
| --- | --- | --- | --- |
| 第一层：背景 | 为什么做？谁用？原来怎么解决？ | 业务理解、动机 | 上来讲技术，讲不清价值 |
| 第二层：方案 | 为什么选 A 不选 B？整体链路？ | 技术判断、系统性 | 只会报名词，没有取舍 |
| 第三层：细节 | 数据多少？显存多少？超参？失败过什么？ | 真实参与度、工程能力 | 数字含糊、归因错误 |
| 第四层：结果与反思 | 指标怎么定义？基线？上线效果？重做怎么改？ | 严谨性、复盘能力 | 指标口径不清、夸大 |

> 一个残酷的判断：如果候选人说不出“失败过什么”，面试官通常默认项目是跟做的，不是主导的。

## 2. 项目回答的通用骨架

### 2.1 90 秒版本（先给结论）

```
我做的是【什么系统】，服务【谁】，解决【什么痛点】。
原来【基线方案】的问题是【量化瓶颈】。
我负责【范围】，核心方案是【1 句话】。
最终【核心指标】从 A 到 B，成本/延迟【变化】。
最大的难点是【1 个】，我们通过【方法】解决。
如果重做，我会【1 个改进】。
```

### 2.2 白板版本（被要求展开时）

画五层：

```
业务/用户
  ↓
数据链路（采集 → 清洗 → 标注 → 评测集）
  ↓
模型/策略（基座 → 训练/微调/对齐 → 推理）
  ↓
服务链路（网关 → 检索/工具 → 模型 → 后处理）
  ↓
观测与反馈（日志 → 指标 → badcase → 迭代）
```

每层只讲“输入、输出、关键决策、失败模式”，不要陷入框架 API。

### 2.3 数字口径卡片

为简历上的每个数字准备一张卡片：

| 问题 | 必须能回答 |
| --- | --- |
| 指标定义 | 公式是什么？分子分母？ |
| 测试集 | 多少条？怎么构造？有没有污染？ |
| 基线 | 对比对象是谁？同参数量/同预算吗？ |
| 显著性 | 提升几个点？方差多大？是否多次运行？ |
| 线上验证 | 灰度比例？观察多久？有无负向指标？ |
| 归因 | 提升来自哪个模块？做过消融吗？ |

### 3.2 重点题参考要点

**Q：为什么要继续预训练，而不是 SFT/RAG？**
- 继续预训练注入的是“分布内知识/语言风格”，适合领域语料量大、知识难以用检索覆盖的场景。
- SFT 主要学指令格式与行为，注入新知识的效率低，且容易灾难性遗忘。
- RAG 适合可检索、可引用的显式知识，不适合隐式风格、术语体系、推理模式。
- 真实方案常组合：继续预训练（可选）→ SFT → RAG；要给出成本与收益对比。

**Q：继续预训练后通用能力下降怎么办？**
- 数据层：加入 10%–30% 通用数据回放；避免领域数据过拟合。
- 训练层：较小学习率、早停、LoRA（如果基座足够强）。
- 模型层：模型合并（Task Arithmetic/TIES）、双模型路由。
- 评测层：建立通用能力回归集，设定下降阈值（如不超过 2 个点）。

**Q：loss spike 怎么排查？**
- 定位：全局还是单 rank、单 step 还是持续、是否伴随梯度范数飙升。
- 数据：异常长度、空样本、重复模板、脏字符。
- 数值：FP16 溢出、attention 全 mask、softmax 过大。
- 优化：学习率、warmup、梯度裁剪、batch size。
- 处理：回滚 checkpoint、跳过异常 batch、切 BF16、降 LR；记录复现条件。

### 4.2 重点题参考要点

**Q：LoRA 的 rank/alpha 怎么选？**
- 先给公式：$W'=W+\frac{\alpha}{r}BA$，$B\in\mathbb{R}^{d\times r}$，$A\in\mathbb{R}^{r\times k}$。
- 任务越复杂、数据越多，rank 可以适当大（16–64）；简单风格适配 8–16 足够。
- alpha 常取 $r$ 或 $2r$，等价于缩放学习率；调 alpha 时固定 rank 做消融。
- 目标模块通常覆盖 q/k/v/o，效果不够再加 MLP；全加参数量上升。
- 用验证集选，不要只看训练 loss；报告 rank/alpha/模块的消融表。

**Q：SFT 后模型变傻，为什么？**
- 数据分布过窄：只学领域格式，通用指令能力被覆盖。
- 数据质量差：短回答、模板化、错误答案。
- 训练过头：epoch 太多、学习率太大，过拟合训练集。
- loss mask 错误：把 prompt 也算了 loss，模型学会复述问题。
- 灾难性遗忘：全参微调更明显；LoRA 也可能。
- 排查：分领域评测、看输出长度分布、对比基座、做数据消融。

**Q：LoRA 不收敛/格式错乱怎么排查？**
- 数据：模板是否与基座 chat template 一致？special token 是否被截断？
- 标签：loss mask 是否只覆盖 assistant？EOS 是否加入？
- 超参：学习率是否过大（LoRA 常用 1e-4 到 2e-4）？rank 是否过小？
- 目标模块：是否只加了 q/v，表达能力不足？
- 数值：BF16/FP16、梯度裁剪、padding 侧。
- 解码：评测时 stop token、temperature 是否与训练一致。

### 5.2 重点题参考要点

**Q：PPO、DPO、GRPO 的核心区别？**
- PPO：on-policy，需要 policy、reference、reward、value 四个模型；用 clip 限制更新；用 GAE 估优势；KL 约束防漂移。
- DPO：off-policy，直接用偏好对优化；隐式奖励 $\beta\log(\pi_\theta/\pi_{\text{ref}})$；不需要 RM 和 value；工程简单，但受离线数据覆盖限制。
- GRPO：on-policy，对同一 prompt 采样一组回答，用组内均值/标准差算优势；去掉 value 模型；适合数学/代码等可验证奖励任务。
- 一句话：PPO 是“RM + critic 的在线 RL”，DPO 是“把 RM 解析掉的离线对比学习”，GRPO 是“用组内相对值替代 critic 的在线 RL”。

**Q：reward hacking 怎么发现和缓解？**
- 表现：reward 持续涨但人工评测下降；输出变长、堆砌套话、谄媚、钻规则漏洞。
- 监控：reward 分布、长度分布、KL、熵、重复率、人工抽检。
- 缓解：KL 惩罚、reward clipping/归一化、长度惩罚、ensemble RM、规则约束、定期人工校准、held-out prompt。
- 根本：reward 只是代理指标，必须和真实目标对齐；对可验证任务用单元测试/答案校验更稳。

**Q：8 张 A100 做 7B GRPO，怎么加速？**
- 显存：LoRA/QLoRA、ZeRO-3/FSDP、offload、activation checkpointing、vLLM 推理。
- 吞吐：增大 rollout batch、动态采样、序列打包、并行采样；训练与推理分离（colocate vs disaggregate）。
- 算法：过滤全对/全错样本（零梯度）、控制最大长度、token-level loss、梯度累积。
- 工程：参考模型与 reward 模型量化/共享、prefix caching、异步 rollout。
- 给出取舍：offload 省显存但降速；增大 batch 提升吞吐但增加延迟。

### 6.2 重点题参考要点

**Q：KV Cache 怎么估？**
- 公式：$2\times L\times n_{kv}\times d_{head}\times S\times B\times \text{bytes}$。
- 7B（32 层、8 KV 头、128 维、FP16）：每 token 约 $2\times32\times8\times128\times2=131$KB；32K 上下文约 4.3GB/请求。
- 70B（80 层、8 KV 头、128 维）：每 token 约 328KB；32K 约 10.5GB/请求。
- 实际还要加权重、激活、框架开销；用 `nvidia-smi` 与框架指标校准。

**Q：吞吐和延迟怎么权衡？**
- 增大 batch 提升吞吐，但排队延迟上升；continuous batching 用 token 级调度缓解。
- chunked prefill 防止长 prompt 阻塞 decode；PD 分离把 prefill 与 decode 放到不同资源池。
- 量化降低带宽压力，提升 decode 速度；但可能损失精度。
- 用 TTFT、TPOT、P99、Goodput 四个指标一起看，不能只看 tokens/s。

**Q：线上事故怎么讲？**
- 现象：P99 飙升/超时/错误率上升/OOM。
- 定位：看 QPS、队列长度、KV Cache 使用率、GPU 利用率、batch 组成。
- 根因：长请求涌入、缓存碎片、某个模型副本故障、上游重试风暴。
- 处理：限流、降级到小模型、扩容、重启副本、清理缓存。
- 复盘：加隔离队列、长度上限、预热、熔断、压测覆盖。

### 7.2 重点题参考要点

**Q：父子索引为什么有效？代价是什么？**
- 子块小，embedding 语义集中，召回精度高；父块大，提供完整上下文，生成质量好。
- 实现：子块检索 → 映射父块 → 去重 → 截断到 token 预算。
- 代价：存储翻倍、映射逻辑复杂、父块可能引入噪声；需要控制父块大小与返回数量。

**Q：为什么 BM25 + 向量？**
- 向量擅长语义相似，但对精确匹配（编号、人名、错误码）不敏感。
- BM25 擅长关键词精确匹配，但不懂同义改写。
- 混合检索用 RRF 或加权分数融合，通常能提升召回；代价是索引与调参复杂度。
- RRF 公式：$\text{score}(d)=\sum_i \frac{1}{k+\text{rank}_i(d)}$，$k$ 常取 60。

**Q：怎么判断是检索错还是生成错？**
- 先看 gold document 是否在召回集合：不在 → 检索问题；在但没被引用 → 排序/上下文组装问题；引用了但答错 → 生成/推理问题。
- 构造分层评测：检索 Recall@k、Context Precision、Faithfulness、Answer Correctness。
- 人工看 50–100 条 badcase，按“未召回/排序低/上下文截断/忽略证据/幻觉/问题歧义”归类。

### 8.2 重点题参考要点

**Q：Workflow、Planner、Policy 分别解决什么？**
- Workflow：预定义控制流，节点和转移确定，稳定、可审计，适合审批/申报。
- Planner：根据状态动态分解任务，适合开放目标，但计划可能不可执行。
- Policy：直接决定下一步动作，本质是状态空间上的策略学习。
- 生产系统通常组合：Workflow 规定权限边界与不可跳过的检查，Planner 生成局部计划，Policy/模型选择具体工具；高风险操作回到确定性节点校验。

**Q：Function Calling 和 MCP 的区别？**
- Function Calling 是模型输出结构化调用意图的机制（工具名 + 参数），由应用执行。
- MCP 是标准化的上下文/工具协议，统一 server 与 client 的接口，让工具可复用、可发现、可跨应用。
- 类比：Function Calling 是“函数调用约定”，MCP 是“USB 接口标准”。
- 工程上 MCP 解决工具生态与接入复用，不替代权限、沙箱、审计。

**Q：Agent 怎么评估？**
- 结果指标：任务成功率、答案正确率、用户满意度。
- 过程指标：步数、工具调用次数、token 成本、延迟、轨迹合规率。
- 鲁棒性：工具报错、超时、歧义指令下的恢复率。
- 安全：越权率、注入成功率、敏感信息泄露。
- 方法：固定任务集 + 模拟环境（WebArena/SWE-bench 风格）+ LLM-as-judge + 人工抽检。

## 11. “数字拷打”清单

面试官最常追问的数字，提前准备口径：

| 数字 | 必须说清 |
| --- | --- |
| 数据量 | 原始/清洗后/去重后/token 数，统计口径 |
| 参数量 | 总参数/激活参数，是否含 embedding |
| 显存 | 参数+梯度+优化器+激活，卡型与精度 |
| 训练成本 | GPU 数 × 小时 × 单价，MFU |
| 吞吐 | tokens/s 还是 req/s，batch/并发条件 |
| 延迟 | 平均/P95/P99，TTFT/TPOT 分开 |
| 准确率 | 测试集大小、基线、绝对值/相对提升 |
| 召回率 | Recall@k，k 是多少，gold 怎么定义 |
| 幻觉率 | 定义（无依据陈述比例）、标注一致性 |
| 成本 | 每千 token/每次请求，含检索与重排 |
| 提升 | 消融归因，是否显著，是否线上验证 |

> 一个实用原则：**任何百分比都要能还原成“分子/分母”**。说不清分母，就等于没做过。

## 12. 项目 red flags 与补救

| Red flag | 面试官的判断 | 补救 |
| --- | --- | --- |
| 只讲框架，不讲数据 | 没真正做过 | 补数据来源、规模、清洗、评测 |
| 指标只给结果，不给基线 | 数字可能编的 | 准备基线、测试集、消融 |
| 说不出失败案例 | 跟做/包装 | 准备 1 个真实失败与修复 |
| 所有模块都“我负责” | 可信度低 | 明确边界，讲协作接口 |
| 方案没有替代对比 | 缺少判断力 | 准备 2 个替代方案与取舍 |
| 上线后没有监控 | 工程经验不足 | 补指标、告警、回滚 |
| 数据量/成本明显不合理 | 没算过账 | 用公式现场估算并说明假设 |

## 13. 三个完整项目答辩示例

### 13.1 企业文档 RAG

- 背景：5000 份制度文档，客服平均查找 6 分钟，答案不一致。
- 基线：关键词搜索 + 人工回复，Top-1 命中 48%。
- 方案：PDF 解析 → 父子块 → BGE embedding + BM25 混合召回 → bge-reranker 精排 → 引用式生成 → 权限过滤。
- 难点：表格切分错、权限泄漏、长文档上下文超限。
- 结果：Recall@5 72%→89%，忠实度 81%→93%，首答时间 6min→20s。
- 反思：表格解析仍是瓶颈；下一步做结构化抽取 + GraphRAG。

### 13.2 7B 领域 SFT + LoRA

- 背景：金融研报问答，通用模型术语不熟、格式不稳定。
- 基线：Qwen2.5-7B-Instruct + few-shot，准确率 61%。
- 方案：清洗 3 万条研报问答，LoRA（r=32，alpha=64，q/k/v/o+MLP），2 epoch，8×A100。
- 难点：合成数据噪声、格式错乱、通用能力下降。
- 结果：领域准确率 61%→78%，通用 MMLU 下降 1.8 个点；训练成本约 120 GPU 小时。
- 反思：数据质量比 rank 更关键；下一步做 DPO 优化引用与拒答。

### 13.3 vLLM 推理优化

- 背景：7B 客服模型，单卡 A10，P99 2.5s，峰值 OOM。
- 基线：HuggingFace generate，batch=1，无 KV 管理。
- 方案：vLLM + PagedAttention + continuous batching + INT4 AWQ + 长度上限 + 前缀缓存。
- 难点：长请求阻塞、量化后格式遵循下降。
- 结果：吞吐 2.3×，P99 1.1s，显存下降 45%；量化导致准确率下降 1.2 个点，通过关键任务不量化兜底。
- 反思：PD 分离与投机解码是下一步；压测要覆盖真实长度分布。

## 14. 面试高频问题（项目 meta 题）

### Q1：介绍一个你最有成就感的项目。
- 用 90 秒骨架，突出“问题难度 + 你的决策 + 量化结果”。
- 选一个能展开技术细节的项目，不要选最大的但说不清。

### Q2：你项目中最大的难点是什么？
- 给一个具体问题，不要泛泛说“数据难”。
- 结构：现象 → 定位 → 尝试过什么 → 最终方案 → 验证 → 残留问题。

### Q3：如果给你更多资源，你会怎么改进？
- 先分清瓶颈：数据、模型、评测、工程。
- 给出优先级与预期收益，不要只堆“更大模型”。

### Q4：你的方案和 XX 竞品/论文比，差在哪？
- 承认差距，给出可比条件（参数量、数据、预算）。
- 说明你的约束与取舍，而不是强行说更好。

### Q5：这个项目里你具体负责什么？
- 明确边界：你做的、协作的、复用的。
- 对协作部分也要能讲清接口与决策，避免“我只写了数据加载”。

### Q6：如果线上效果不好，你怎么排查？
- 分层：数据/检索 → 模型 → 编排 → 服务 → 用户。
- 先看 badcase 分布，再做消融/对照，最后灰度验证。
