# Agent 与工具调用：从范式到工程可靠性

## 本章导读

智能体（Agent）不是“更聪明的聊天机器人”，而是让模型在循环中观察环境、调用工具、根据结果调整计划的系统。  
本章先划清 Agent 与固定工作流（workflow）的边界，再讲 ReAct、Plan-and-Execute 等范式，最后落到工具协议、记忆、多智能体与安全。  
面试中真正区分候选人的，往往不是能否背出概念，而是能否说清楚“什么时候不该用 Agent”以及“如何让它不失控”。  
文中的步数、成本、成功率均为量级估算，协议与产品能力以公开资料为准。

## 核心要点

- Agent 的本质是“模型决策 + 工具执行 + 循环反馈”，自主性来自循环，风险也来自循环。
- 任务确定性高、延迟敏感、容错低时，优先用 workflow，而不是让模型自由规划。
- 工具描述与参数 schema 的质量，直接决定工具调用准确率。
- 可靠性的四道闸门是最大步数、超时、预算与人类审批，缺一不可。
- 记忆要区分“当前任务状态”和“跨会话知识”，两者写入与检索策略完全不同。
- 多智能体不是默认答案，通信开销与责任扩散常让效果低于单 Agent。
- 评估要看任务成功率、步骤效率与轨迹质量，不能只看最终答案。

## 1. Agent 的定义与能力边界

### 1.1 什么是 Agent

一个可工作的 Agent 通常由五部分组成：大语言模型（Large Language Model，LLM）作为决策核心；工具集（tools）用于读写外部世界；记忆（memory）保存上下文与历史；执行循环（loop）负责多步推进；策略与护栏（policy and guardrails）约束行为边界。

形式化地，Agent 在每一步根据状态 $s_t$ 选择动作 $a_t$，环境返回观察 $o_t$，直到满足终止条件：

$$ a_t \sim \pi_{\theta}(\cdot \mid s_t),\quad s_{t+1}=s_t\oplus(a_t,o_t) $$

其中 $\pi_{\theta}$ 是模型策略，$\oplus$ 表示把动作与观察追加到状态。所谓“自主”，指的是动作序列由模型在运行时决定，而不是由开发者预先写死。

### 1.2 与 workflow 的区别

| 维度 | 固定工作流（workflow） | Agent |
| --- | --- | --- |
| 控制流 | 开发者预定义节点与边 | 模型运行时决定下一步 |
| 可预测性 | 高 | 低 |
| 调试难度 | 低，可按节点定位 | 高，需轨迹回放 |
| 覆盖场景 | 步骤稳定、规则清晰 | 步骤随输入变化、需要探索 |
| 成本与延迟 | 稳定可控 | 随步数波动，可能放大 |
| 失败模式 | 单点失败，易兜底 | 循环、漂移、工具滥用 |
| 典型例子 | 发票审核流水线 | 开放式调研、故障排查 |

实践中常见的是“workflow 骨架 + Agent 节点”：外层流程确定，内层某一步需要模型自主选择工具时，才引入小范围 Agent。这样既保留可控性，又获得灵活性。

### 1.3 什么时候不该用 Agent

- 任务步骤固定且可枚举，用状态机或流程图更便宜、更可靠。
- 对延迟有硬性要求，例如在线交易风控，循环带来的多轮推理无法满足。
- 错误代价极高且难以回滚，例如直接执行资金操作，应改为“建议 + 人工审批”。
- 工具本身不稳定或缺少幂等保障，Agent 的重试会放大副作用。
- 没有可观测性与评估手段，出了问题无法定位，不应上线。

判断标准可以概括为：任务是否需要“运行时决策”。如果答案是“不需要，只是步骤多”，那它应该是 workflow。

## 2. 主流范式

### 2.1 ReAct

ReAct（Reasoning and Acting）让模型交替输出推理与动作：先说明要做什么、为什么，再调用工具，拿到观察后继续推理。它的优势是推理过程与外部证据交错，能根据观察纠错；缺点是每步都要一次模型调用，延迟与成本随步数线性增长，且推理文本可能不忠实。

ReAct 适合：需要外部检索、计算、查询状态的多步任务。不适合：单步就能完成的任务，以及工具调用本身很慢的场景。

### 2.2 Plan-and-Execute

Plan-and-Execute 先让模型生成完整计划，再逐步执行，执行器可以在子任务失败时重规划。相比 ReAct 的“边想边做”，它的全局性更强，适合长任务与需要并行子任务的场景。缺点是初始计划可能基于错误假设，且计划与执行脱节时会反复返工。

工程上常用“粗计划 + 细 ReAct”：上层列出 3 至 7 个里程碑（估算），每个里程碑内部用 ReAct 完成。

### 2.3 Reflection

Reflection 让模型对自己的输出或轨迹进行批评，再根据批评修订。常见形式是“生成—批评（critique）—修订”两到三轮。它能提升代码、写作等可自检任务的质量，但对事实性错误帮助有限，因为没有新增外部信息。风险是模型自我批评也会错，且容易陷入“越改越啰嗦”。

使用要点：批评要针对明确标准（正确性、格式、引用）；限制轮数；保留原始版本以便回退；有条件时引入外部验证器（测试、编译器、检索）。

### 2.4 Tree of Thoughts

思维树（Tree of Thoughts，ToT）把推理展开为树：每个节点是一个中间状态，模型生成多个候选，评估器打分，再用广度或深度搜索推进。它适合需要回溯的规划、谜题、组合优化。代价是调用次数成倍增长，且评估器质量决定搜索效果。多数业务场景用线性 ReAct 加一次重规划即可，不必上 ToT。

### 2.5 范式对比

| 范式 | 规划方式 | 调用成本 | 纠错能力 | 适用任务 |
| --- | --- | --- | --- | --- |
| ReAct | 隐式、逐步 | 中 | 中，依赖观察 | 工具型多步任务 |
| Plan-and-Execute | 显式、先全局 | 中高 | 中，可重规划 | 长任务、可并行 |
| Reflection | 事后批评 | 高 | 高（可自检任务） | 代码、写作 |
| ToT | 搜索式 | 很高 | 高 | 规划、组合问题 |

## 3. 工具调用

### 3.1 Function Calling 的 schema

工具调用（function calling）本质是让模型输出结构化的调用意图，由宿主程序校验并执行。一个清晰的模式（schema）应包含：工具名、用途描述、参数类型、必填项、枚举范围、单位与格式、以及失败时的行为。

```json
{
  "name": "query_order",
  "description": "按订单号查询订单状态。仅当用户提供订单号或已确认身份后调用。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "pattern": "^[A-Z0-9]{10,20}$"},
      "include_logistics": {"type": "boolean", "default": false}
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

描述要写“何时用、何时不用”，而不只是“这个工具做什么”。模型在多个相似工具之间选择时，负面约束比正面描述更有效。

### 3.2 参数校验与执行

模型生成的参数不可信，必须在服务端做三层校验：结构校验（JSON Schema）、语义校验（订单号是否存在、日期是否合法）、权限校验（当前用户能否操作该资源）。校验失败应返回结构化错误，让模型有机会修正，而不是直接抛异常终止。

```python
from pydantic import BaseModel, ConfigDict, Field, ValidationError

class QueryOrderArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")      # 拒绝未声明的多余参数
    order_id: str = Field(pattern=r"^[A-Z0-9]{10,20}$")
    include_logistics: bool = False

def call_tool(name, raw_args, user):
    try:
        args = QueryOrderArgs(**raw_args)          # 结构与类型校验
    except ValidationError as e:
        return {"ok": False, "error": "invalid_args", "detail": e.errors()}
    if not acl.can_read(user, "order", args.order_id):  # 权限校验
        return {"ok": False, "error": "permission_denied"}
    return order_service.query(args.order_id, args.include_logistics)
```

### 3.3 并行调用与依赖

同一轮中互不依赖的工具可以并行，例如同时查天气、汇率、库存。宿主程序应解析多个调用请求，做依赖分析，能并行则并行，有依赖则串行。并行要注意：结果顺序要与调用对应；任一失败是否回滚；下游限流与幂等。

不要让模型自己“记住”哪个结果对应哪个调用，消息协议里要用调用 ID 显式关联。

### 3.4 错误重试与幂等

错误要分类处理：参数错误不重试，交给模型修正；权限错误不重试，直接告知用户；限流与超时可退避重试；服务端 5xx 可有限重试；业务规则拒绝不重试。退避可用指数加抖动：

$$ t_i=\min\Big(t_{max},\ t_0\cdot 2^{i}\cdot\big(1+U(0,1)\cdot j\big)\Big) $$

其中 $U(0,1)$ 为随机数，$j$ 为抖动系数。重试必须配合幂等键（idempotency key），否则“扣款超时后重试”可能扣两次。写操作的工具应支持去重表或幂等令牌，读操作才适合无条件重试。

### 3.5 工具设计原则

- 单一职责：一个工具只做一件事，避免“万能执行器”。
- 窄参数：用枚举与格式约束缩小模型出错空间。
- 可预览：高风险操作先试运行（dry-run），返回将要发生什么。
- 可回滚：写操作提供撤销或补偿接口。
- 有分页：列表类工具必须支持 limit 与 cursor，防止上下文爆炸。
- 有配额：按用户与任务限制调用次数与金额。

## 4. MCP 的定位与基本概念

模型上下文协议（Model Context Protocol，MCP）是一个开放协议，用于把模型应用与外部数据源、工具以标准方式连接起来。它解决的是“每个模型客户端都要为每个工具写一套适配”的重复建设问题。

核心角色有三类：宿主（host）是面向用户的应用；客户端（client）由宿主创建，与单个服务器保持连接；服务器（server）暴露能力。通信基于 JSON-RPC 2.0，常见传输包括标准输入输出（stdio）与流式 HTTP（Streamable HTTP）。早期还有 HTTP+SSE 传输，已逐步被替代，具体以公开资料为准。

服务器侧常见原语包括：工具（tools），可被模型调用并产生副作用；资源（resources），只读的上下文数据；提示（prompts），可复用的模板。客户端侧还涉及采样（sampling）、根目录（roots）与交互式补充（elicitation）等能力。实际实现要关注能力协商与版本兼容。

MCP 与 function calling 不是替代关系：function calling 规定模型如何表达调用意图，MCP 规定宿主如何发现、连接并调用外部服务。前者是模型接口，后者是集成协议。MCP 的引入也扩大了攻击面，接入第三方服务器时要审查其权限、网络出口与数据留存策略。

## 5. 记忆

### 5.1 四类记忆

| 类型 | 载体 | 生命周期 | 写入方式 | 主要风险 |
| --- | --- | --- | --- | --- |
| 短期上下文 | 消息窗口 | 单次会话 | 直接追加 | 超长、关键信息被挤掉 |
| 摘要记忆 | 滚动摘要 | 单次或跨会话 | 超阈值时压缩 | 摘要失真、丢失细节 |
| 长期向量记忆 | 向量库 | 跨会话 | 抽取事实后写入 | 错误记忆固化、隐私 |
| 结构化状态 | 数据库/状态机 | 任务周期 | 按字段更新 | schema 漂移、并发冲突 |

短期上下文负责“正在发生什么”，摘要记忆负责“聊过什么”，长期记忆负责“用户是谁、偏好什么”，结构化状态负责“任务进行到哪一步”。四者混在一段 prompt 里，既浪费 token，也难以控制一致性。

### 5.2 写入与检索策略

长期记忆不应把每轮对话原样写入。推荐流程是：抽取候选事实（用户偏好、身份、长期目标）→ 去重与冲突检测 → 置信度打分 → 写入并附来源与时间 → 定期衰减或归档。写入要有用户可见的开关与删除能力，满足隐私要求。

检索时不能只看向量相似度，还要考虑时间衰减、来源可靠性与任务相关性：

$$ \text{score}(m)=\alpha\cdot\text{sim}(q,m)+\beta\cdot e^{-\lambda\Delta t}+\gamma\cdot\text{confidence}(m) $$

其中 $\Delta t$ 为记忆年龄，$\alpha,\beta,\gamma$ 为权重。检索到的记忆要标注时间，避免把旧偏好当成当前事实。写入与读取都要做权限隔离，防止跨用户记忆泄漏。

## 6. 多智能体

### 6.1 常见组织方式

- 角色分工：规划者、执行者、审查者各司其职，适合可分解的长任务。
- 通信协作：通过共享黑板或消息总线交换中间结果。
- 辩论：多个 Agent 给出不同答案并互相质疑，最后由裁判汇总，适合开放性判断。
- Agent-to-Agent（A2A）：跨系统、跨厂商的 Agent 互操作协议，关注能力发现、任务委派与状态同步，仍在演进，以公开资料为准。

### 6.2 常见失败

| 失败 | 表现 | 根因 | 缓解 |
| --- | --- | --- | --- |
| 死循环 | 两个 Agent 反复请求同一信息 | 缺少终止条件与状态推进 | 步数上限、去重、仲裁者 |
| 责任扩散 | 都以为别人会做，关键步骤遗漏 | 分工边界不清 | 显式任务清单与负责人 |
| 成本爆炸 | 调用次数随 Agent 数平方增长 | 全连接通信 | 星型拓扑、消息预算 |
| 上下文丢失 | 转交后接手的 Agent 不知道前情 | 状态未结构化传递 | 共享状态与摘要协议 |
| 共识错误 | 互相附和而非纠错 | 同质模型、缺乏证据 | 引入异质模型与外部验证 |

多智能体适合“任务可并行、角色差异明显、需要独立审查”的场景。若只是把一个任务拆给多个同样的模型，通常单 Agent 加工具更划算。

## 7. 工程可靠性

### 7.1 四道闸门

1. 最大步数：硬限制循环次数，例如 8 至 15 步（估算），超过则返回中间结果并说明。
2. 超时：单步超时与任务总超时分别设置，工具调用要有独立超时。
3. 预算：限制 token、金额、工具调用次数，按任务累计，超限即停。
4. 人类审批：高风险写操作必须人工确认，审批界面要展示参数与影响范围。

### 7.2 沙箱与权限

代码执行、浏览器操作、文件读写都应在沙箱（sandbox）内进行：限制文件系统范围、网络出口、可用命令与运行时长；每次执行使用临时环境；输出做大小截断。权限遵循最小化原则：工具使用独立凭证，按用户身份做资源级鉴权，不用管理员账号跑所有请求。

### 7.3 可观测性

一次 Agent 运行要记录完整轨迹（trace）：输入、每步的模型输出、工具名与参数、返回摘要、耗时、token、错误码、最终状态。轨迹要能按任务 ID 回放，便于定位“是模型选错工具，还是工具返回错”。指标至少包括：成功率、平均步数、工具错误率、超时率、单任务成本、人工介入率。

日志要脱敏，工具返回可能包含个人信息，不能原样长期保存。生产环境建议采样存储完整轨迹，其余保留摘要与指标。

## 8. 评估

### 8.1 核心指标

$$ \text{SuccessRate}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\text{task}_i\ \text{succeeded}] $$

$$ \text{AvgSteps}=\frac{1}{N}\sum_{i=1}^{N}\text{steps}_i,\quad \text{ToolAcc}=\frac{\#\text{correct tool calls}}{\#\text{total tool calls}} $$

任务成功率是主指标，但要看定义：是最终答案正确，还是环境状态正确，还是人工验收通过。步骤效率衡量“是否绕远路”，工具调用准确率可分工具选择、参数正确、时机正确三个维度。

### 8.2 轨迹评估

轨迹评估不只看终点，还看路径：是否调用了必要工具、是否重复无效调用、是否越权、是否在错误后恢复。可用规则检查（必须调用 A 再调用 B）、关键节点匹配、以及大模型作为评审（LLM-as-judge）对轨迹打分。LLM 评审要看证据与步骤，不能只给一个笼统分数。

### 8.3 评测集设计

评测集要覆盖：单工具、多工具串行、并行、工具失败、参数缺失、权限拒绝、需要澄清、无法完成。每类 20 至 50 条（估算），并为每条定义可判定的成功标准与环境初始状态。Agent 评估需要可重置的环境，否则前一次运行的副作用会污染后一次。

## 9. 安全

### 9.1 主要威胁

- 提示注入（prompt injection）：攻击者把指令藏在网页、文档、邮件或工具返回中，诱导 Agent 偏离原任务。
- 工具滥用：Agent 被诱导调用删除、转账、发信等高风险工具。
- 数据外泄：把敏感上下文拼进 URL、邮件或第三方工具请求中。
- 混淆代理（confused deputy）：Agent 拥有高权限，攻击者借它访问本无权访问的资源。
- 供应链风险：第三方 MCP 服务器或插件本身恶意。

### 9.2 防御措施

| 威胁 | 防御 | 局限 |
| --- | --- | --- |
| 直接注入 | 指令层级、输入分类器、拒绝越权请求 | 新变体可绕过 |
| 间接注入 | 把工具返回视为不可信数据、分隔标记、内容消毒 | 无法完全区分数据与指令 |
| 工具滥用 | 最小权限、白名单（allowlist）、高风险操作人工审批 | 审批疲劳会降低效果 |
| 数据外泄 | 出口白名单、敏感信息脱敏、URL 域名校验 | 合法渠道仍可能泄漏 |
| 混淆代理 | 按用户身份鉴权、短期令牌、资源级授权 | 实现复杂，易漏配 |

核心原则是“永不信任模型输出”：模型可以提议动作，但执行前必须由确定性代码做权限与参数校验。安全不能只靠提示词（prompt）里写“不要做坏事”。

## 10. ReAct 循环的最小实现

```python
def react_agent(question, registry, max_steps=8, timeout_s=60):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": question}]
    start, seen = time.time(), set()
    for step in range(max_steps):                      # 闸门一：步数上限
        if time.time() - start > timeout_s:            # 闸门二：总超时
            return {"status": "timeout", "trace": messages}
        action = llm.chat(messages, tools=registry.schemas())
        if action.type == "final":                     # 停止条件：模型给出终答
            return {"status": "ok", "answer": action.content, "trace": messages}
        key = (action.name, json.dumps(action.args, sort_keys=True))
        if key in seen:                                # 停止条件：重复动作
            return {"status": "stuck", "trace": messages}
        seen.add(key)
        try:
            result = registry.call(action.name, action.args)   # 内部做校验与鉴权
        except ToolError as e:
            result = {"error": str(e), "retryable": e.retryable}
        messages.append(action.to_message())
        messages.append({"role": "tool", "content": json.dumps(result, ensure_ascii=False)})
    return {"status": "max_steps", "trace": messages}   # 闸门三：预算耗尽
```

这段代码省略了 token 预算、人工审批与轨迹落盘，但三个停止条件是生产实现的底线：步数、时间、重复动作。缺任何一个，都可能出现无限循环或成本失控。示例对相同工具与参数直接判停；生产环境应结合观察是否变化，避免误杀轮询类工具。

## 面试高频问题

### 1. Agent 和 workflow 的本质区别是什么？

**参考回答要点：**

- 区别在控制流由谁决定：workflow 由开发者预定义，Agent 由模型在运行时选择下一步。
- Agent 带来对开放输入的适应性，也带来不可预测性、调试难度与成本波动。
- 步骤稳定、容错低、延迟敏感的场景应优先 workflow。
- 常见架构是 workflow 骨架内嵌小范围 Agent，而不是全流程放开。

### 2. 什么时候不应该用 Agent？

**参考回答要点：**

- 任务步骤可枚举且规则清晰，用状态机更可靠。
- 对延迟或成本有硬约束，多轮循环无法满足。
- 高风险写操作且不可回滚，应改为建议加人工审批。
- 缺少可观测性、评估集与回滚手段时，不应直接上线。

### 3. ReAct 的优缺点是什么？

**参考回答要点：**

- 优点是推理与外部观察交错，能根据工具结果纠错，适合多步信息获取。
- 缺点是每步一次模型调用，延迟与成本随步数增长。
- 推理文本可能不忠实，模型可能“先有结论再编理由”。
- 需要配合步数上限、重复检测与工具结果校验。

### 4. 如何提升工具调用准确率？

**参考回答要点：**

- 工具描述写清“何时用、何时不用”，相似工具要做区分。
- 参数用 JSON Schema 约束类型、枚举、格式与必填项。
- 服务端做结构、语义、权限三层校验，错误结构化返回给模型修正。
- 用真实失败案例构造评测集，持续回归工具选择与参数填写。

### 5. 工具调用失败如何重试？

**参考回答要点：**

- 先分类：参数与权限错误不重试，限流、超时、5xx 可有限重试。
- 用指数退避加抖动，设置最大次数与总超时。
- 写操作必须带幂等键，避免重试造成重复扣款或重复下单。
- 重试仍失败时返回可解释错误，让 Agent 换工具或向用户澄清。

### 6. MCP 解决了什么问题？

**参考回答要点：**

- 把模型应用与外部工具、数据源的连接标准化，减少 M 乘 N 的适配工作。
- 基于 JSON-RPC，定义工具、资源、提示等原语与能力协商。
- 与 function calling 互补：前者是集成协议，后者是模型表达调用的接口。
- 引入第三方服务器后攻击面扩大，需要审查权限、出口与数据留存。

### 7. Agent 的记忆应该如何设计？

**参考回答要点：**

- 区分短期上下文、摘要记忆、长期向量记忆与结构化任务状态。
- 长期记忆先抽取事实、去重、冲突检测，再带来源与时间写入。
- 检索时综合相似度、时间衰减与置信度，并标注记忆时间。
- 提供用户可见的查看、删除与关闭能力，做好权限隔离。

### 8. 多智能体为什么经常不如单 Agent？

**参考回答要点：**

- 通信开销随 Agent 数量增长，信息在转交中丢失或失真。
- 责任扩散导致关键步骤无人负责，出错后难以归因。
- 同质模型互相附和，辩论退化为共识幻觉。
- 只有在任务可并行、角色差异明显、需要独立审查时，多智能体才有稳定收益。

### 9. 如何评估一个 Agent？

**参考回答要点：**

- 主指标是任务成功率，要明确是答案正确、环境状态正确还是人工验收。
- 辅助指标包括平均步数、工具调用准确率、超时率、单任务成本与人工介入率。
- 轨迹评估看必要工具是否调用、是否重复无效动作、错误后能否恢复。
- 评测环境要可重置，评测集覆盖工具失败、权限拒绝、需澄清与不可完成。

### 10. 如何防范 Agent 的提示注入与工具滥用？

**参考回答要点：**

- 把网页、文档、工具返回都视为不可信数据，不用其覆盖系统指令。
- 执行前由确定性代码做权限与参数校验，高风险操作强制人工审批。
- 最小权限、短期凭证、网络出口白名单，限制横向移动与数据外泄。
- 记录完整轨迹并做异常检测，发现越权尝试及时阻断与告警。
